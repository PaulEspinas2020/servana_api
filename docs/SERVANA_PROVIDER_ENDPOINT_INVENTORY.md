### P0 — the legacy family

All 30 sit in `technician.routes.ts`. They are already documented in
`WORKER_ROUTE_MIGRATION.md`, have authenticated successors, and carry traffic
telemetry (`legacyRouteTelemetry`). **Both client apps have now been migrated
off them** (ServanaWorker `b94f7a1`, ServanaClient `0c8af75`), which was the
blocker on deleting the block. They stay reachable until those builds are in
the field and observed traffic reaches zero.

Until then the exposure is live: anyone can read a provider's job cards —
which carry the customer's name, phone number and home address — follow a
provider's live position, or accept and complete bookings on their behalf.

## What this audit could NOT determine

Stated explicitly so nothing here is mistaken for more than it is.

- **Response schemas are not fully typed.** The backend uses raw `pg` with no
  ORM or serializer layer, so response shape is whatever each handler
  assembles inline. Shapes were compared by reading handlers pairwise, not
  derived from a schema. There is no generated contract to diff against — that
  is what §3 (OpenAPI) would create.
- **`clients` is textual.** A path appearing in a repository is not proof a
  screen reaches it. The provider portal, for instance, lists the whole legacy
  family in `servana-backend-capabilities.config.ts`, which is a catalogue and
  not a call site. Live callers were confirmed by hand only where a finding
  depended on it.
- **Ownership enforcement inside services was not traced end to end.** Several
  handlers take a path id under `verifyAuth` and enforce ownership in SQL
  (`WHERE worker_uid = $1`). That is correct but invisible at this level, so a
  P2 grade means *worth tracing*, not *proven vulnerable*.
- **Status vocabularies were not reconciled.** That is §6 and needs the
  database's own constraints, not route source.

## Corrections this audit makes to earlier records

- **Command 2 recorded that job actions send `?workerUid=` and marked it
  UNVERIFIED whether the backend trusts it.** It does not:
  `actingWorkerUid` (`technicianController.ts:510`) returns `fromToken ?? null`
  and logs a mismatch. The parameter was decorative. Now removed client-side.
- **An earlier pass of this audit reported all 10 chat routes as
  unauthenticated.** That was wrong. `chat.routes.ts:8` applies
  `router.use(verifyAuth)` at the router level; the extractor only inspected
  per-route middleware. Corrected, and the extractor now counts router-level
  middleware. No chat vulnerability exists.
- **`GET /api/:id` (`booking.routes.ts:44`) is a bare single-segment wildcard**
  registered before 15 other routers. It shadows nothing *today* — no later
  router declares a competing single-segment GET — but any future one would be
  silently swallowed. Latent, not live.
