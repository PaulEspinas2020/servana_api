# The published request contract — what a write requires, permits, and refuses

**TAB 03 of the Servana Backend Master Command (worker/provider mobile).**
Written 2026-08-21 against `067c9a0`. Backend only. Nothing pushed or deployed.

---

## What was measured before building

The Master Command describes the gap as: *the contract extract clients consume
carries method, path, domain, idempotent and replayMechanism, and no
required-body data.*

Measured in `docs/api/CANONICAL_CALL_MANIFEST.json`, the artifact a client team is
told to diff its call sites against:

| | Book | Measured |
|---|---|---|
| Write operations in the extract | — | **55** |
| Carrying required-body data | 0 | **0** |
| Carrying permitted-body data | 0 | **0** |
| Carrying `additionalProperties` strictness | 0 | **0** |
| Carrying `replayMechanism` | *"it carries it"* | **0** |
| Carrying a version or digest | — | **0** |

The gap was one field **wider** than the book states: `replayMechanism` was not
published either, and the book's own TAB 03 mandate relies on it being there.

## Why this mattered, measured rather than predicted

Eight provider-mobile writes shipped sending bodies this backend refuses. All
eight passed the client's own tests, because those tests asserted the **path**. A
path assertion proves a call is routable and says nothing about whether it is
acceptable.

The one that should alarm is device registration: it sent `deviceToken` where the
field is `token`. Its failure mode is not an error anybody sees — it is **push
notifications never arriving**, and push is how a provider learns a job exists.

This was never a client-competence gap. The information already existed in
`SCHEMAS`; it was simply never published where a client would read it.

## What is published now

Every entry in `CANONICAL_CALL_MANIFEST.json` carries:

```jsonc
{
  "id": "provider.profile.patch",
  "method": "PATCH",
  "path": "/api/v1/provider/profile",
  "requestSchema": "ProviderProfilePatch",
  "requiredBody": ["clientRequestId"],
  "allowedBody": ["biography", "clientRequestId", "displayName",
                  "experienceSummary", "languages", "skills"],
  "additionalBodyAllowed": false,
  "replayMechanism": ["client-request-id"]
}
```

And at the document level: `contractSha256`, `contractDigestHeader`,
`bodyEnforcement`, `writeCount`, `writesWithDeclaredBody`.

### `null` is not `[]`

An operation that declares **no** request body publishes `null` for all three
body fields — never empty arrays. The two mean different things, and an empty
allow-list would read to a client as *"no field is permitted"*, which would gate
out every call. Eight of the 55 writes are bodyless (path-parameter operations
like `DELETE /notifications/{key}` and `POST /auth/logout`); 47 declare a schema.

### Derived, not maintained

`requestContractOf` reads `SCHEMAS` — the same map `buildOpenApiDocument()`
renders. One source, two views. A hand-maintained second copy is exactly what
this avoids, and a test asserts the extract equals a fresh derivation.

### It refuses what it cannot read

Every request schema today is a plain object — measured across all 47, not one
uses `$ref`, `allOf`, `oneOf` or `anyOf` at the top level. A future one might.
If the derivation answered that with `allowedBody: []`, the extract would look
complete while telling every client that no field is permitted. So it **throws**,
naming the schema. A composed request schema is a build failure asking somebody
to teach one function about composition, rather than a client outage nobody
attributes to it.

### Staleness is now detectable — mandate 4

`contractSha256` is the sha256 of the OpenAPI document **the running process
serves**, and every `/api/v1` response already carries the same value in the
`x-contract-sha256` header. A client compares its pinned manifest's digest
against a live header; a mismatch means its copy is old.

That comparison is against a **server**, not a git checkout. It is deliberately
not a timestamp: this artifact is regenerated by `convergence:docs:check` on
every gate run, and a clock in it would fail the check on an unchanged contract.

---

## The finding that qualifies all of the above

**Nothing in this backend validates a request body against these schemas.**

There is no Ajv, no Joi, no Zod, and `register.ts` never reads `requestSchema`.
Every handler enforces its own preconditions in code — `patchProviderProfile`'s
`clientRequestId` regex, `providerMayEdit`'s field filter, and so on.

So the schemas are the **documented intent**, and the extract publishes that. A
client should read `requiredBody` as *"the handler refuses without this"*, not as
*"a validator rejects this"*.

This is stated **in the artifact itself** — `"bodyEnforcement": "handler"` — not
only here. Without it, a client that got away with sending an extra field to one
of the 12 endpoints that permit extras could reasonably conclude the whole
extract was wrong, and stop trusting it.

TAB 01 found this distinction is not academic. The `photo` field was permitted by
one allow-list, refused by another, and the OpenAPI schema was **right** while
the code was wrong. A published contract and an enforced one are different
objects, and the gap between them is where these defects live.

## Proof: the eight defects, as a permanent gate

`tests/v1-request-contract-extract.test.ts` pins each of the eight to the data
that would have caught it, and runs a client-shaped gate over a body matching the
defect:

| # | The defect | Caught by |
|---|---|---|
| 1 | `verify-mobile` sent `{phone, code}`; `idToken` is required | required + strict |
| 2 | `me/devices` sent `deviceToken`; the field is `token` | required + strict |
| 3 | `provider/documents` omitted two required fields | required |
| 4 | `time-off` omitted `reason` | required |
| 5 | `provider/profile` omitted `clientRequestId` | required |
| 6 | `disputes` omitted `category` | required |
| 7 | `additional-work` sent a pair where `items` is a list | required + strict |
| 8 | job-cancel invented two fields against a strict schema | strict |

**8 of 8 detectable**, with one honest limitation published rather than hidden:
defect 3's endpoint does **not** declare `additionalProperties: false`, so the
*wrong-name* half of that defect is a warning a client may raise, not a refusal
the server makes. `additionalBodyAllowed: true` says so. 35 of the 47 declared
schemas are strict; 12 are not, and no schema was tightened here — the mandate
was to publish what is already enforced, and changing what is enforced is a
different task with a different blast radius.

The general properties are asserted separately, because eight pins cannot grow:
every write states a body contract or states it has none; every required field is
also a permitted one; every non-idempotent write publishes a replay mechanism
beside its fields; the extract equals a fresh derivation; and every array is
sorted, so regenerating an unchanged contract is not a diff.

Mutation-verified: returning `[]` instead of `null` for a bodyless write fails
it, and so does dropping the sort.

---

## Not changed

No schema was tightened. No runtime behaviour changed. This TAB publishes
information that already existed, which is why the book calls it the lowest-risk
and highest-leverage item in the programme — and the measurement agrees: the
diff is one derivation function, one generator stamp, and a test.
