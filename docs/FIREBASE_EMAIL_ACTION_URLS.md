# Firebase email action URLs — the console half

Password-reset and email-verification links are generated by the Firebase Admin
SDK. **Two settings decide where the person ends up, and only one of them is
code.** This document covers the other one, because the code half is already
done and does not work on its own.

---

## What the code already does

`src/constants/platformContinueUrls.ts` resolves a caller-supplied *platform
name* to a `continueUrl` and passes it as `ActionCodeSettings`:

| `platform` | Reset link returns to | Verification link returns to |
| --- | --- | --- |
| `customer` | `CUSTOMER_RESET_URL` → `https://servana.com.ph/reset-password` | `CUSTOMER_VERIFY_URL` → `https://servana.com.ph/verify-email` |
| `provider` | `PROVIDER_RESET_URL` → `https://provider.servana.com.ph/provider/reset-password` | unset — the provider portal has no verify-email route |
| anything else, or absent | nothing | nothing |

The caller sends a **name**, never a URL. A reset link whose return address the
caller controls is a credential-phishing primitive wearing Firebase's domain.

---

## Why the code half is not enough

`generatePasswordResetLink(email, { url })` produces a link to **Firebase's**
action handler with `continueUrl` attached:

```
https://<project>.firebaseapp.com/__/auth/action
    ?mode=resetPassword
    &oobCode=...
    &continueUrl=https://servana.com.ph/reset-password
```

With the project's **default** action handler, the person:

1. opens the link,
2. resets their password **on a Firebase-branded page**,
3. is offered a "Continue" link to `continueUrl`.

That is already better than before — previously step 3 did not exist and the
journey simply ended on a page that was not Servana. But they still start
somewhere that is not Servana, and `/reset-password` never receives the
`oobCode`.

To have them land **directly** on Servana's own page holding the `oobCode`, the
project's action URL must be repointed. Then the same link becomes:

```
https://servana.com.ph/reset-password
    ?mode=resetPassword
    &oobCode=...
    &apiKey=...
    &continueUrl=...
```

which is the shape both Servana reset pages already parse.

## The console procedure

Firebase project **`servana-59bee`** — the only Servana Firebase project. SMS
quota, test numbers and region policy are shared across every app in it, so
changes here are platform-wide.

1. Firebase console → **Authentication** → **Templates**.
2. Pick **Password reset**. Click the pencil, then **customise action URL**.
3. Set it to the page that will handle the code.
4. Repeat for **Email address verification**.
5. Save, then send yourself one of each and open them.

### The decision that has to be made first

There is **one** action URL per project, and **two** portals that want it —
customer (`servana.com.ph`) and provider (`provider.servana.com.ph`). They
cannot both have it.

Options, in the order they are worth considering:

- **Point it at the customer portal.** The customer portal has both
  `/reset-password` and `/verify-email` built and tested. The provider portal
  keeps today's behaviour (Firebase's page plus a "Continue" link home), which
  is what it has always had. Lowest risk, and it is the portal with the larger
  expected audience.
- **Point it at a small shared handler** that reads `continueUrl` and forwards
  to the right portal. Correct for both, but it is a new deployable that does not
  exist.
- **Leave it on the default.** Everyone gets a "Continue" link home. Nothing
  breaks; nothing improves beyond what the code change already delivered.

Do **not** point it at the provider portal today: the provider portal has no
`verify-email` route, so email verification would land on a 404.

### After repointing

The receiving page must tolerate arriving **without** an `oobCode` — Firebase
also uses the action URL for modes the page does not handle. Both Servana pages
already do: the customer portal's `/reset-password` renders a "request a new
link" state, and the provider portal's bails to `invalid_token`.

## The environment half

Optional. Every variable has a default and boot fails loudly on a malformed one.

```
PROVIDER_RESET_URL=https://provider.servana.com.ph/provider/reset-password
CUSTOMER_RESET_URL=https://servana.com.ph/reset-password
CUSTOMER_VERIFY_URL=https://servana.com.ph/verify-email
# PROVIDER_VERIFY_URL — leave unset until the provider portal has the route
ADMIN_PORTAL_URL=https://admin.servana.com.ph
```

Production env file: `/home/github-runner/env/servana_api.env`. Restart with
`pm2 restart servana-prod` afterwards. Watch the first lines of
`pm2 logs servana-prod` — `assertContinueUrlsAreUsable()` runs **before**
`listen`, so a typo is a startup failure naming the variable, not a silent
mis-send.

### One value worth checking against reality

`PROVIDER_RESET_URL` previously defaulted to
`https://servana.com.ph/provider/reset-password`. The provider portal declares
its own origin as `https://provider.servana.com.ph` (`environment.prod.ts`), and
`servana.com.ph` is the origin assigned to the *customer* portal — whose router
sends every unknown path to a 404. So unless production sets this variable,
provider password resets were landing on a page that could not help them.

The default is now the provider portal's own declared host. **Confirm what
production actually has set**, because this file cannot see it:

```
ssh root@<server> "grep -E 'RESET_URL|VERIFY_URL|PORTAL_URL' /home/github-runner/env/servana_api.env"
```

## Verifying it end to end

Use a synthetic account. Never a real customer's address.

1. `POST /api/auth/forgot-password` with `{ "email": "...", "platform": "customer" }`.
2. Open the email. The link's `continueUrl` query parameter should be the
   customer reset URL.
3. If the action URL has been repointed, you land on `servana.com.ph/reset-password`
   with an `oobCode`. If it has not, you land on Firebase's page and reach
   Servana by "Continue". **Both are expected** — which one you see is the test
   of whether the console change has been made.
4. Repeat with `"platform": "provider"`, and with the field omitted. Omitted must
   produce a link with **no** `continueUrl` — that is the case that proves the
   mobile apps are unaffected.

## What must never be added to the allowlist

`mobile` and `web`.

`mobile` would hand a link to a flow that sends 6-digit codes, and neither
Flutter app can receive a link anyway: neither has an `oobCode` screen, an
Android intent-filter, or an iOS associated-domains entitlement. `web` is sent
by more than one Servana web app as a signup default, so resolving it would
redirect one of them to the other's pages.

There is a test asserting both stay out (`tests/platform-continue-urls.test.ts`).
