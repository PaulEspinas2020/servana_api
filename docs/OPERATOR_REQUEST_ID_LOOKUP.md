# Looking up a request id

An operator has quoted a reference from a failed screen. This is what it opens.

> TAB 09 of the Admin API Master Command: *"An operator can now read out
> `req_01J9ZK…`; nobody can currently turn it into the server log line that
> explains the failure. Until then the id is a token with no lock."*
>
> There are two locks. Neither was written down, and one of them was broken.

## First: which kind of id is it?

| Shape | What it means | What to do |
| --- | --- | --- |
| `local-a3f9…` | The failure **never reached the server** — a template threw while rendering, or the request never left the browser. | Stop. There is no server log line to find. This is not a missing entry. |
| Anything else | The request reached the API. | Continue below. |

The `local-` prefix is generated by the admin portal. The shape of the string is
the operator telling you, without knowing it, that the server never saw this.

## Lock 1 — the audit trail, for anything an admin *did*

Every audited admin action records the request id. This is queryable **through
the API**, by anyone with the permission — no shell, no host access:

```
GET /api/admin/audit-logs?request_id=<the id>
```

It answers *what did this action do*: actor, outcome, before/after state,
changed fields, reason, entity, and the exact time.

Backed by `admin_audit_events.request_id`, written by `recordAuditEvent` and
filtered in SQL by `findEvents`. `tests/request-id-joinable.test.ts` asserts the
predicate against the production statement builder rather than a
re-implementation of it, so this cannot quietly stop working.

**This covers approvals, rejections, assignments, permission changes, refund
decisions, catalog publishes — the actions an operator is normally asked about.**

## Lock 2 — the structured request log, for everything else

A failure that is *not* an audited action — a 500 on a read, a validation
refusal, a timeout — is emitted as one structured JSON line per request:

```bash
ssh root@<prod-host>
pm2 logs servana-prod --lines 5000 --nostream | grep '<the id>'
```

The line carries `requestId`, method, route template, status, latency, actor
role and client — and deliberately **no** request body, response body, query
string or headers. It will tell you *what failed and how fast*; it will not tell
you what was in the payload, by design.

### The limitation, stated plainly

This needs a shell on the production host. It is a file, not a queryable store,
and it rotates. **That is the part TAB 09 asks for that is still open**, and
closing it is infrastructure work — a log sink — rather than a code change.

Until then, the honest position is: an audited action is fully traceable through
the API; an unaudited failure is traceable only by someone with host access.

## Sampling — why a 200 might not be there

2xx and 3xx on hot read routes are **sampled**. Everything else is always
logged, because a 4xx or 5xx is why somebody opens the log in the first place.

So the absence of a line for a *successful* request is expected and means
nothing. The absence of a line for a *failed* one is a real signal — start by
checking whether the id is a `local-` one.

## The defect this document was written alongside

`helpers/adminError` used to mint a **fresh** `randomUUID()` for every legacy
admin error and stamp it over the correlation id the middleware had already set.

The consequence was precise and invisible: the log line and the audit row both
carried the *real* correlation id, and the operator was handed a *different*
number. Searching for it found nothing — not because the log was missing, but
because the id had never existed anywhere else. Across 251 admin operations.

It now reads the id back off the response, where `correlationMiddleware` put it.
If you are investigating a failure from **before** that fix shipped, an admin
error id that matches nothing is expected and is not evidence the log was lost.

## For the person who has the id but not the access

`GET /api/admin/audit-logs?request_id=` is the one to try first. It needs a
token and the audit-log permission, not a shell, and it answers the majority of
questions that get asked.
